This project is an open-source, published as is. It is not intended to be used in production.

## File Structure (Core + Transport Wrappers)

Legacy stdio shim (deprecated, still supported):

- `catalyst_center_enhanced_declarative.py` -> use `catalyst_center_stdio.py`

Current suite (preferred):

- `catalyst_center_core.py` - self-contained core logic
- `catalyst_center_stdio.py` - stdio wrapper
- `catalyst_center_remote.py` - streamable HTTP wrapper

### Proof-of-Concept Server
The following server demonstrates auto-generation of MCP tools and management of multiple Catalyst Center clusters.

### Catalyst Center MCP Server (`catalyst_center_stdio.py`)  
- **Purpose**: Cisco Catalyst Center on-premises network automation
- **Features**: Device inventory, compliance checking, issue tracking, configuration management
- **API Coverage**: Sites, devices, clients, assurance data, operations
- **API Explorer**: Use Catalyst Center API specs file for Cosine search of APIs. Identify APIs, call the APIs, provide API docs and API telemetry. Restricted to only call GET API endpoints.
- **Local LLM offloading** _(optional)_: Route tool responses through a local OpenAI-compatible LLM before returning to Claude. Reduces token consumption by 85–99% on large responses. See [TUTORIAL Section 9](TUTORIAL.md#9-local-llm-offloading) for setup and benchmark results.

### Remote Streamable HTTP Servers
The following wrapper exposes the same toolset over streamable HTTP transport:

**Wrapper architecture note:** Remote server in this repo is a thin transport wrapper over `catalyst_center_core.py`.  
All tool logic (including API explorer safety rules and method restrictions) lives in `_core`, which keeps stdio and remote behavior in sync.  
Legacy shim is a compatibility entrypoint only and routes to the current stdio/core flow.
- **Purpose**: Remote HTTP wrapper for `catalyst_center_core.py`
- **Transport**: Streamable HTTP on `/mcp` (default port `8000`)
- **API Explorer Safety**: Read-only explorer behavior inherited from declarative server (GET-only; no POST/PUT/DELETE)
- **Sync Model**: Inherits declarative server logic (no duplicated execution engine)

## Quick Start

1. **Install dependencies**
   ```bash
   make install
   ```

2. **Configure credentials**

   ```bash
   make env
   # then edit environment.env with CC_URL, CC_USER, CC_PASS
   ```

3. **Download the embedding model** (one-time, required for API Explorer)

   ```bash
   make model
   ```

4. **Smoke-test the server** (optional — verify it starts before wiring it to your MCP client)

   ```bash
   make smoke
   ```

5. **Configure your MCP client** to launch `catalyst_center_stdio.py` — see [VS Code Copilot Integration](#vs-code-copilot-integration) or [Claude Desktop Configuration](#claude-desktop-configuration) below.

6. **Run the remote HTTP wrapper** (only needed when your MCP client connects over HTTP instead of stdio)

   ```bash
   make remote
   # or: make remote HOST=127.0.0.1 PORT=9000
   ```

7. **Legacy Stdio Shim (Deprecated but Supported)**

   ```bash
   uv run python catalyst_center_enhanced_declarative.py
   ```

## Configuration

### Core Configuration Files

- `catalyst_config.yaml` - Catalyst Center API endpoints and parameters
- `pyproject.toml` - Python dependencies including MCP, API clients, ML libraries

**Location note:** Runtime cluster config file is loaded from the `Resources/` directory:
- `Resources/catalyst_center_clusters.yaml`

### API Explorer Swagger Files

- `Resources/cc_swagger.json` - Catalyst Center OpenAPI/Swagger source used by `catalyst_center_core.py` explorer features

These files are used for endpoint discovery, similarity search, endpoint metadata, and explorer analytics workflows.

**Note:** API explorer auto-discovery and dynamic execution are intentionally restricted to `GET` endpoints only.  
`POST`/`PUT`/`DELETE` operations are not auto-generated by explorer tools and must be executed only through explicit declarative tools defined in YAML.

### Transformer Model Resource

- Local model cache base directory: `embeddings_cache/`
- Expected model path: `embeddings_cache/model/all-MiniLM-L6-v2`
- Model download helper: `download_model.py`

Example:
```bash
make model ARGS="--no-ssl-verify"
# or with a custom model name:
uv run python download_model.py --model-name all-MiniLM-L6-v2
```

### Tool Catalog

- `Resources/MCP_Tools.md` - Markdown catalog of declarative and explorer tools for Catalyst Center

### Logging

- `logs/catalyst_center_mcp.log`

### Multi-Environment Setup

**`Resources/catalyst_center_clusters.yaml`** - Configure multiple Catalyst Center clusters:
```yaml
catalyst_centers:
  - name: "Portland"
    host: "Portland-center.domain.com"
    version: "2.3.7.10"
    location: "Portland"
    enabled: true
  - name: "San Jose"
    host: "SanJose-catalyst.domain.com"
    version: "2.3.7.9" 
    location: "San Jose"
    enabled: false
```

### Environment Variables

Copy the example file and fill in your values:
```bash
cp environment.example.env environment.env
```

Then edit `environment.env` with your Catalyst Center credentials:
```bash
CC_URL=https://your-catalyst-center.domain.com
CC_USER=your_username
CC_PASS=your_password
```

> `environment.example.env` documents all available options including optional local LLM offloading.

## VS Code Copilot Integration

### Prerequisites

- VS Code with the **GitHub Copilot** extension installed and signed in
- Dependencies installed (`make install`) and credentials configured (`make env`)

### Configuration

Add the server to `.vscode/mcp.json` in your project root (create the file if it doesn't exist):

```json
{
  "servers": {
    "catalyst_center": {
      "type": "stdio",
      "command": "/path/to/your/.venv/bin/python3",
      "args": ["/path/to/your/catalyst_center_stdio.py"]
    }
  }
}
```

Replace the paths with your actual virtual environment and script locations, e.g.:
```json
{
  "servers": {
    "catalyst_center": {
      "type": "stdio",
      "command": "${workspaceFolder}/.venv/bin/python3",
      "args": ["${workspaceFolder}/catalyst_center_stdio.py"]
    }
  }
}
```

> VS Code manages the server lifecycle — it starts and stops `catalyst_center_stdio.py` automatically. You do not need to run it manually.

### Using the tools

Once configured, the MCP server starts automatically when VS Code opens the workspace. Tools are available in:

- **Copilot Chat** (`Ctrl+Alt+I` / `Cmd+Option+I`) — ask natural language questions about your network
- **Copilot Edits / Agent mode** — tools are called automatically when relevant

Example prompts in Copilot Chat:

```
Show me all active P1 issues
Which devices are non-compliant with their golden config?
Run 'show ip route' on device 192.168.255.5
How many sites are in the inventory?
```

### Troubleshooting

- **Server not starting**: Check the Output panel (`View → Output`) and select `GitHub Copilot` or `MCP` from the dropdown for error logs.
- **Tools not appearing**: Open the Command Palette (`Cmd+Shift+P`) and run `MCP: List Servers` to verify the server is running.
- **Credential errors**: Ensure `environment.env` is present in the project root with valid `CC_URL`, `CC_USER`, and `CC_PASS` values.

## Claude Desktop Configuration

### Stdio

```json
{
  "mcpServers": {
    "catalyst_center_stdio": {
      "command": "/path/to/your/.venv/bin/python3",
      "args": ["/path/to/your/catalyst_center_stdio.py"]
    }
  }
}
```

**Note**: Update the paths to match your actual `.venv` and script locations. Claude Desktop manages the server lifecycle automatically.

### Remote (Streamable HTTP)

Start the remote server first:
```bash
make remote
# or: make remote HOST=127.0.0.1 PORT=9000
```

Add to your Claude Desktop `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "catalyst_center_remote": {
      "url": "http://127.0.0.1:8000/mcp"
    }
  }
}
```

Each server provides declarative tools plus AI-powered API exploration for complete network automation capabilities.
